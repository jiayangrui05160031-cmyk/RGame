# RGame 持续优化设计：战斗可读性、内容扩容与流畅度

日期：2026-08-19  
范围：本地开发分支 `agent/rgame-improvement-local`  
状态：用户已授权开始本地推进；未验收前不推送 GitHub。

## 1. 目标

RGame 的下一阶段不是简单增加 PNG 数量，而是让每一份资产都服务于明确的玩法反馈：

- 玩家能迅速看懂当前状态、危险和奖励。
- 不同关卡有自己的视觉主题和战斗节奏，而不是只换背景颜色。
- 新武器、新敌人、新地图具备完整闭环：配置、逻辑、渲染、音效/特效、测试。
- 大量敌人和特效同时出现时保持稳定帧率，避免重复缩放、重复创建 Surface 和无界增长的反馈队列。
- 所有修改可回滚、可追踪、可在本地验收。

## 2. 设计原则

### 2.1 借鉴方向

只借鉴成熟游戏经过验证的交互原则，不复制受版权保护的素材、代码或具体界面：

- **Vampire Survivors / Brotato**：自动攻击游戏中，信息层级必须优先服务于移动、危险和构筑选择。
- **Hades II**：重要事件、受击、暴击和 Boss 阶段需要有清晰的多通道反馈，而不是只改变一行文字。
- **Risk of Rain 2**：每个场景需要有独立的色彩、地形和事件记忆点。
- **Archero**：升级选择要让玩家能一眼比较收益和构筑方向。
- **元气骑士**：角色、武器和敌人的轮廓在小尺寸下也必须可辨认。

这些原则会转化为 RGame 自己的“火星轨道战”视觉语言：深色玄武岩背景、青蓝能量、熔金危险色、紫色虚空和少量暖白高光。

### 2.2 不破坏现有核心

- 第一阶段不重写 `Engine.tick`。
- 先把测试和资源校验补齐，再调整战斗数值。
- 内容数据优先通过现有 `ConfigBundle` 接入。
- 渲染层增加缓存和纯布局函数，不把 pygame 依赖带入核心库。
- 可选资产缺失时使用现有几何 fallback。

## 3. 三种实施路线与选择

### 路线 A：先全面重做美术和 UI

优点：视觉变化最快。  
缺点：没有测试护栏，容易掩盖逻辑问题；资产和代码接入可能错位。  
结论：不采用。

### 路线 B：只修代码，不扩内容

优点：风险低。  
缺点：无法解决游戏内容单调、场景记忆点不足和资产利用率低的问题。  
结论：不采用。

### 路线 C：护栏优先的纵向切片扩容

先完成一个可验证切片，再复制模式扩展：

1. 建立本地日志、测试、资源和 headless 基线。
2. 优化 UI 状态层和渲染缓存。
3. 完成一个新地图主题 + 一个新敌人 + 两把新武器 + 对应图标、投射物和反馈。
4. 本地真实运行与性能检查。
5. 用户验收后再进入下一切片。

结论：采用路线 C。它能同时满足“优化代码”“增加资产”“不乱改”和“持续推进”。

## 4. 分阶段路线图

### Phase 0：工程基线

范围：`pyproject.toml`、CI、`tests/`、资源校验、README、开发日志。

验收：

- `python -m pytest -q` 可运行。
- `python main.py --headless --seed 42` 通过。
- 资源校验不依赖开发者本机绝对路径。
- CI 与本地命令一致。
- README 与实际仓库结构一致。

### Phase 1：UI 与流畅度

范围：`rgame/render/pygame_app.py`、`theme.py`、布局纯函数和渲染缓存。

设计：

- 统一 HUD 间距、层级、边框、字体和语义色。
- 菜单使用“轨道舱”布局：左侧标题/世界状态，中部主操作，右侧构筑摘要。
- 战斗 HUD 保持中央视野干净，把生命、经验、分数、关卡、武器槽固定在边缘。
- 卡牌选择显示：稀有度、即时增益、与当前构筑的关联、替换风险。
- Boss HUD 采用阶段色带 + 破防条 + 弱点标识 + 技能预警。
- 将布局计算抽为纯函数，在 960x540、1280x720、1920x1080 三种尺寸测试。
- 对背景、精灵、UI art、字体和 glow 做缓存；限制反馈对象数量；不在每帧创建可复用的大型 Surface。
- 低帧率时降低装饰层和非关键粒子密度，不降低核心命中判定。

### Phase 2：内容纵向切片

先新增一组完整内容，而不是同时散落添加十几个半成品：

- 新地图：能源矿区/废弃轨道站，拥有独立背景、边缘装饰、动态图层和事件色彩。
- 新敌人 A：矿脉寄生体，近战分裂/短冲刺，受伤时外壳破裂。
- 新敌人 B：轨道炮台，远程蓄力，预警线清晰，发射后短暂暴露核心。
- 新武器 A：磁轨长弓，蓄力后高穿透，命中反馈偏冷蓝。
- 新武器 B：熔核无人机，围绕玩家巡航，周期性发射小型追踪脉冲。
- 每个新实体都有：配置 ID、中文名、平衡参数、素材路径、fallback、渲染规则、至少一个单元/集成烟测。

若外部美术资源尚未制作，先使用项目既有风格的程序化占位资产或现有可组合资源，保证逻辑先可玩；正式 PNG 进入后只替换资源，不改玩法接口。

### Phase 3：关卡与地图机制

- 让地图配置包含背景、边缘装饰、环境事件、危险区域和推荐敌人池。
- 地图机制通过事件总线进入引擎，避免渲染器直接读写核心状态。
- 每关至少有一个“只在本关发生”的视觉或行为记忆点。
- 地图装饰放置在边缘安全区，不能遮挡弹道、敌人和玩家。

### Phase 4：发布质量

- 完善中英文 README、CHANGELOG、资源授权说明。
- 打包后重新验证资源是否进入 wheel。
- CI 加入配置契约、资源清单、headless 长局烟测和构建包启动。
- 版本号、配置版本、日志版本保持一致。

## 5. 修改流程与日志

每一轮遵循：

1. 从当前本地分支读取真实文件和 Git 状态。
2. 在 `docs/development/OPTIMIZATION_LOG.md` 记录本轮目标和范围。
3. 先增加测试或校验，再修改实现。
4. 运行语法检查、单元测试、headless smoke 和必要的渲染检查。
5. 记录失败、原因、修复和最终命令输出摘要。
6. 形成独立本地 commit，方便用户查看和回滚。
7. 用户验收通过后，才允许推送 GitHub。

## 6. 资产接入契约

新增 PNG 不以“放进目录”为完成标准，必须满足：

- 路径和 ID 与加载表一致。
- PNG 为真实 RGBA，透明边缘合格。
- 32x32、64x64、128x128 缩放后仍能识别主体。
- 缺失时有 fallback，不影响启动。
- 至少有一处实际渲染或反馈路径使用它。
- `verify_assets` 能报告存在、尺寸、模式和透明度。
- 资源不能包含文字、水印、棋盘格或不应出现的底板。

## 7. 性能验收指标

第一阶段先记录基线，再对比改动后结果：

- 固定 seed 下 headless 运行 120 秒不崩溃。
- 敌人达到高密度时不出现对象数量无界增长。
- 1280x720 窗口下，正常战斗目标为稳定 60 FPS；无法达到时记录最低帧率和触发场景。
- 资源重复缩放命中缓存，不在每帧重新 smoothscale 同一尺寸。
- UI 布局在最小支持尺寸不重叠、不越界。

## 8. 当前实施顺序

本地下一步按以下顺序执行：

1. 修正资源校验脚本的绝对路径问题，增加可配置根目录。
2. 补齐 pytest 开发依赖和最小核心测试基线。
3. 增加配置契约、资产清单和 headless 长局 smoke。
4. 优化 UI 布局和字体缓存，先做不改变玩法的安全改动。
5. 在本地生成并接入第一批风格统一的新增占位资产。
6. 加入第一个新地图/敌人/武器纵向切片。
7. 完成本地验收，更新日志，等待用户验收。
